43 - API Contract

Purpose

This document defines the first-level API contract for the Loyalty Platform.

It describes business actions, request and response expectations, authorization boundaries and idempotency requirements.

It is not yet a complete OpenAPI specification.

The final OpenAPI document must be derived from this contract.

⸻

API Principles

The API represents business actions.

Every business action is owned by exactly one Business Engine.

API endpoints orchestrate requests but never duplicate business rules implemented by the owning Engine.

The API must not expose direct database operations.

Prefer:

* Join Loyalty Program
* Record Receipt
* Redeem Reward Points
* Cancel Receipt

Avoid:

* Create Reward Transaction
* Update Membership Balance
* Delete Receipt

⸻

Base Path

/api/v1

Breaking changes require a new API version.

⸻

Common Headers

Authorization

Authorization: Bearer <access_token>

Used by Customer, Employee, Manager and Business Owner clients.

⸻

Idempotency

Idempotency-Key: <unique_client_key>

Required for financially relevant operations.

⸻

Request Tracking

X-Request-ID: <unique_request_id>

Optional from clients.

Generated by the Platform when omitted.

⸻

API Integration Key

X-API-Key: <integration_key>

Used only by approved external integrations.

⸻

Standard Success Response

{
  "success": true,
  "data": {},
  "metadata": {
    "request_id": "string",
    "timestamp": "ISO-8601"
  },
  "errors": []
}

⸻

Standard Error Response

{
  "success": false,
  "data": null,
  "metadata": {
    "request_id": "string",
    "timestamp": "ISO-8601"
  },
  "errors": [
    {
      "code": "BUSINESS_ERROR_CODE",
      "message": "Human-readable message",
      "field": null
    }
  ]
}

Errors must never expose internal implementation details.

* device_id

* device_id

* access_token
* refresh_token

Possible events:

* PhoneVerificationSucceeded
* CustomerAuthenticated

Refresh Session

POST /auth/refresh

Input:

* refresh_token

Response:

* access_token

⸻

Receipt API

Preview Purchase

Purpose:

Calculate expected outcomes without recording a Receipt.

Input:

* membership_token
* location_id
* receipt_total
* currency

Returns:

* expected Reward Points
* pending or immediate availability
* expected XP
* possible redemption value
* active Benefits
* applicable promotions

⸻

Record Receipt

POST /receipts

Used by Employee App.

Required:

* membership_token
* location_id
* receipt_number
* fiscal_device_id or manual_source_id
* receipt_total
* currency
* receipt_timestamp
* idempotency key

Returns:

* receipt_id
* processing_status
* estimated Reward result
* estimated XP result
* redemption result, when included
* async_processing_pending

Primary event:

* ReceiptRecorded

⸻

Record Receipt through Integration

POST /integrations/receipts

Produces the same domain result as POST /receipts.

Integrations must not bypass Business Engines.

Asynchronous Responses

When downstream Event processing is pending, the API may return:

{
  "success": true,
  "data": {
    "resource_id": "string",
    "processing_status": "accepted"
  },
  "metadata": {
    "request_id": "string"
  },
  "errors": []
}

HTTP status:

202 Accepted

Clients may retrieve final processing status from the relevant resource endpoint.

API Security Rules

* Every Customer action is bound to the authenticated Customer.
* Every Business action is bound to an authorized Business role.
* Every Employee action is restricted to assigned Locations.
* Every Integration API Key is scoped to one Business and explicit capabilities.
* Internal IDs may be returned as opaque API resource identifiers but must never be embedded in public QR payloads.
* Financial operations require idempotency.
* Direct ledger mutation endpoints are forbidden.
* Direct balance update endpoints are forbidden.
* Direct Status update is forbidden except through an audited adjustment action.
